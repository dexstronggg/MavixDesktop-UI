# MavixDesktop — Техническое описание

Документ составлен в соответствии с ГОСТ 19.402-78 «Описание программы» и
ГОСТ 19.503-79 «Руководство системного программиста».

---

## 1. Аннотация

Документ содержит техническое описание программы «MavixDesktop» —
наземной станции (Ground Control Station, GCS) системы дистанционного
управления БПЛА «Mavix». Программа устанавливается на персональный
компьютер пилота под управлением Linux. Документ предназначен для
разработчиков и системных администраторов.

---

## 2. Общие сведения

### 2.1. Наименование

Полное наименование: «Наземная станция Mavix» (MavixDesktop).
Условное обозначение: `mavixdesktop`.
Версия: 0.1.0.

### 2.2. Программное обеспечение

| Компонент | Версия |
|---|---|
| Язык программирования | Python ≥ 3.11 |
| GUI-фреймворк | PySide6 ≥ 6.6 |
| WebRTC | aiortc ≥ 1.14, < 1.16 |
| HTTP/WebSocket клиенты | aiohttp, websockets |
| Хранение учётных данных | keyring (с резервом — файл JSON) |
| Видео | PyAV, NumPy |
| Джойстик | pygame |

### 2.3. Назначение

Программа выполняет роль наземной станции пилота:

- проводит аутентификацию пилота на сервере «MavixServer»;
- отображает список собственных БПЛА с указанием состояния (онлайн /
  оффлайн);
- устанавливает WebRTC-сессию с выбранным дроном;
- отображает видеопоток с бортовых камер;
- передаёт команды управления (CRSF) и/или сообщения MAVLink в
  направлении полётного контроллера;
- запускает QGroundControl при наличии и взаимодействует с ним через
  UDP-сокет.

---

## 3. Функциональное назначение

### 3.1. Класс решаемых задач

Программа реализует роль отвечающего (answerer) в WebRTC-сессии:
получает SDP-оффер от дрона через сервер сигнализации, формирует
SDP-ответ, принимает медиа-поток и data-каналы. Дополнительно ведёт
контроль качества канала (см. §4.4) и пишет метрики в файл.

### 3.2. Ограничения

- В каждый момент времени отображается видео не более одного дрона.
- Программа предназначена для работы под GNU/Linux. Запуск под
  Windows и macOS не поддерживается официально, но возможен.
  Автозапуск QGroundControl работает и под Windows (поиск `.exe`
  в типовых каталогах установки либо указание пути вручную); под
  macOS автопоиск не реализован, путь можно задать вручную.

### 4.2. Описание основных модулей

#### 4.2.1. Модуль координатора (`coordinator.py`)

Реализует основной цикл:

1. Подключение к серверу сигнализации с экспоненциальной задержкой.
2. Маршрутизация входящих сообщений по типам:
   - `drones` → обновление списка;
   - `sdp` (оффер от дрона) → `WebRTCManager.handle_offer`;
   - `ice` → `WebRTCManager.handle_ice`;
   - `drone_disconnected` → запоминание `drone_id` для авто-переподключения;
   - `auth_warning` → автоматический REST-refresh JWT;
   - `auth_refreshed` → обновление токена в `SignalClient`;
   - `shutdown` → разрыв сессии без остановки цикла (для последующего
     переподключения).
3. Передача пакетов FC и обработка сообщений `config-channel`
   (`fc`, `cameras`, `battery`, `command_ack`, `fc_armed`, `stats`,
   `statustext` — дрон → GCS; `bitrate`, `params`, `calibrate`,
   `keyframe`, `focus` — GCS → дрон). Форматы GCS → дрон:
   - `bitrate`: `{'type': 'bitrate', 'updates': [{'device_index': N, 'bitrate_kbs': B}, ...]}`;
   - `params`: `{'type': 'params', 'updates': [{'device_index': N, 'param_index': I}, ...]}`;
   - `calibrate`: `{'type': 'calibrate'}`;
   - `keyframe`: `{'type': 'keyframe'}` — запрос ключевого кадра при
     потерях > 2 %, росте числа фризов или отсутствии свежих кадров
     (условия и триггеры — §4.2.3; таймер качества опрашивает их раз
     в секунду);
   - `focus`: `{'type': 'focus', 'device_index': N}` — активная камера
     (борт сбрасывает остальные через `valve`).
   В `stats` борта дополнительно приходит `ice_type`
   (`host`/`srflx`/`relay`/`unknown`) — тип ICE-пары для диагностики
   пути трафика.
4. Запуск/останов `MavlinkRelay` в зависимости от типа FC.

#### 4.2.2. Модуль WebRTC-сессии (`webrtc/`)

`PeerSession` обёртка над `aiortc.RTCPeerConnection`. В роли отвечающего:

1. Получает оффер: `await pc.setRemoteDescription(offer)`.
2. Создаёт ответ: `answer = await pc.createAnswer()`.
3. Применяет ответ: `await pc.setLocalDescription(answer)`.
4. Возвращает SDP-ответа координатору для отправки.

Data-каналы создаются дроном, передаются клиенту через событие
`pc.on('datachannel')`. По метке (`label`) идентифицируются как
`packet`, `ping`, `config` и оборачиваются соответствующими классами
из `channels.py`.

Для приёма видео `peer.py` при создании `RTCPeerConnection` подменяет
`aiortc` JitterBuffer на `DeadlineJitterBuffer` (`webrtc/jitter_patch.py`).
Причина: в aiortc потерянный RTP-пакет останавливает выдачу кадров до
переполнения буфера (до ~0,5 с на 30 к/с) — `_remove_frame` упирается в
дыру и не сдвигает `origin`. Патч (только видео, `is_video=True`) даёт
дыре deadline 200 мс на ретрансмиссию (RTX/NACK), после чего отбрасывает
неполный кадр, сдвигает `origin` дальше и возвращает PLI-флаг (запрос
ключевого кадра). При идеальной сети поведение идентично оригиналу.
Подмена обёрнута в `try/except` — если aiortc изменится, патч просто не
применится, приложение работает дальше.

#### 4.2.3. Модуль пользовательского интерфейса (`ui/`)

Реализован на PySide6. Структура экранов:

| Экран | Файл | Назначение |
|---|---|---|
| Вход | `login_page.py` | Аутентификация по адресу электронной почты и паролю |
| Список дронов | `screens/drone_list_page.py` | Карточки доступных дронов |
| Просмотр дрона | `screens/drone_view/page.py` | Видео + панель управления |
| Настройка джойстика | `screens/joystick_setup.py` | Калибровка осей и кнопок |
| Полётный режим | `screens/flight_window.py` | Полноэкранный режим с отображением стиков |

Горячие клавиши (единый текст справки — `screens/help_text.py`, показывается
по кнопке «i» в окне просмотра и в полётном режиме):

| Клавиши | Действие | Где работает |
|---|---|---|
| `←` `→` | предыдущая / следующая камера | просмотр, полёт |
| `S` / `ы` | таблица качества канала | просмотр |
| `Esc` | выход из полётного режима (сначала закрывает справку) | полёт |
| `i` / `ш` | справка | просмотр, полёт |

Обработчики сравнивают и код клавиши, и `event.text()`, поэтому буквенные
сочетания работают в обеих раскладках.

**Переключение камер.** Кнопки и клавиши `←`/`→` (просмотр и полёт)
переключают активную камеру. В окне просмотра колбэки `on_prev`/`on_next`
вызывают `VideoManager.shift_cam(±1)`; в полётное окно тот же метод
передаётся параметром `shift_cam` (`App._open_flight_window`) — при его
отсутствии полётное окно использует локальный фолбэк: сдвиг индекса по
модулю числа камер. `shift_cam` циклически меняет `_cam_index` по числу
принятых видео-треков, планирует показ активного трека и оповещает
приложение колбэком `on_cam_changed`. `App._on_cam_changed` обновляет
панель настроек камеры, отправляет на борт сообщение `focus` (активная
камера) и сразу запрашивает ключевой кадр — чтобы картинка нового
потока появилась без ожидания PLI.

**Запрос ключевого кадра.** `App._maybe_request_keyframe` (вызывается
каждую секунду из `_tick_quality` по таймеру качества) отправляет борту
сообщение `keyframe` (`_request_keyframe`), если выполняется хотя бы одно
из условий:

- потери `loss_pct` > 2 %;
- счётчик фризов `freeze_count` вырос относительно прошлого тика;
- кадры не обновлялись дольше `_KEYFRAME_STALE_MS` = 1000 мс — метрика
  `staleness_ms` из `LinkSnapshot` (время с последнего показанного кадра);
  это восстанавливает картинку, когда кадры не приходят вовсе (зависший
  или чёрный экран).

Смена камеры вызывает запрос безусловно (минуя условия выше), троттлинг
отсутствует — таймер качества естественно ограничивает частоту.

Связь UI с асинхронной частью программы выполняется через
`Bridge` — объект-носитель сигналов PySide6:

- `client_list_updated(list)` — изменён список дронов;
- `config_received(list)` — получен список камер от дрона;
- `fc_info_received(str, str)` — получена информация о полётном
  контроллере (тип и имя);
- `drone_went_offline(str)` — дрон перестал быть доступен;
- `connect_failed(str)` — не удалось подключиться к дрону;
- `error_occurred(str)` — ошибка соединения с сервером;
- `battery_updated(int, float)` — обновлена телеметрия батареи
  (заряд в процентах и напряжение);
- `session_reset()` — сессия с дроном завершена (разрыв или переподключение),
  UI возвращается к списку дронов.

#### 4.2.4. Модуль связи с FC (`fc/`)

`encoder.build_rc_frame(throttle, roll, pitch, yaw, armed)` —
преобразует положения стиков (в диапазоне [-1; 1]) в кадр CRSF
(тип 0x16, 16 каналов, порядок TAER).

`JoystickInput.is_armed()` содержит защёлку «require-disarm-on-entry»:
пока с момента создания input не зафиксирован DISARM, метод возвращает
False. Это исключает мгновенный арм при входе в полёт с тумблером,
оставленным в ARM (актуально для axis-тумблеров). Защёлка общая для всех
веток (MAVLink-listener в `app.py`, CRSF/MAVLink-поток `FlightWindow`),
так как все они читают arm через этот метод.

`MavlinkRelay` обеспечивает двунаправленный мост:

- от дрона: получаемые байты записываются в локальный UDP-сокет
  (по адресу `QGC_HOST:QGC_PORT`, по умолчанию `127.0.0.1:14550`);
- от QGroundControl: получаемые байты отправляются в `packet-channel`
  WebRTC.

Реализован на `asyncio.DatagramProtocol` через
`loop.create_datagram_endpoint`, что исключает использование
дополнительных потоков.

**Передача калибровки джойстика в QGroundControl.** Требуется
QGroundControl 5.0.8 (Stable). Он собран на SDL2 и хранит калибровку
джойстика в «легаси»-разделе `[Joysticks/<имя>]` файла настроек `.ini`
(Linux: `~/.config/QGroundControl*/`; Windows: `%APPDATA%\QGroundControl`;
macOS: `~/Library/Preferences` и `~/.config`). Ключи раздела:
`RollAxis`/`PitchAxis`/`YawAxis`/`ThrottleAxis` — индексы осей SDL,
назначенные функциям, `Calibrated4=true` включает готовую калибровку,
а `Axis<N>Min/Max/Trim/Rev/Deadbnd` — параметры каждой оси. Формат
`JoystickSettingsV2` (Daily/мастер) на 5.0.8 не читается.

`qgc/joystick_config.py` пишет эти ключи напрямую перед запуском QGC
(`ui/app.py:_apply_calibration_to_qgc`, вызывается из
`_handle_joystick_selected`), тем же классом `QSettings` с `IniFormat`,
которым пользуется сам QGC (на Windows он принудительно выставляет
`QSettings::setDefaultFormat(IniFormat)`) — формат файла (percent-encoding
имён, `\` вместо `/` внутри составного ключа) совпадает с тем, что пишет
сам QGC. Точная калибровка (диапазон/trim/мёртвая зона) для осей,
остающихся в работе, снимается до записи и восстанавливается — ручная
подстройка в QGC не теряется.

Назначение осей пишется в конвенции Mode 2, поэтому в разделе
`[Joysticks]` фиксируется глобальный `TXMode_MultiRotor=2` (режим
трансмиттера QGC хранит по типам ЛА: `TXMode_FixedWing`, `TXMode_MultiRotor`
и т.д.), а в `[JoystickManager]` — `ActiveJoystick=<имя>`.

`SDL_GAMECONTROLLERCONFIG` в 5.0.8 **читается** (mavlink/qgroundcontrol#12639)
и передаётся QGC при запуске. Если устройство опознано как game controller,
в `RollAxis` и т.п. QGC ожидает логические индексы осей SDL (leftx=0,
lefty=1, rightx=2, righty=3) — модуль переводит их из сырых индексов
pygame через нашу SDL-строку калибровки (`sdl_gamecontrollerconfig`);
для обычного raw-джойстика пишутся сырые индексы.

#### 4.2.5. Модуль хранения учётных данных (`server/token_store.py`)

При первом входе пилота refresh-токен сохраняется в системном
хранилище секретов (gnome-keyring / KWallet / Windows Credential
Manager / macOS Keychain). При недоступности хранилища используется
резервный JSON-файл `~/.config/mavixdesktop/tokens.json`. Access-токен
не сохраняется (выпускается заново при каждом запуске).

### 4.3. Расширение протокола сигнализации

Программа использует следующие специфичные сообщения сервера:

- `auth_warning` — запускается процедура REST-refresh;
- `auth_refreshed` — обновляет `SignalClient.access_token`.

### 4.4. Контроль качества канала

Модуль `ui/managers/quality.py` (`LinkQuality`) сводит шесть метрик из трёх
источников и отдаёт их интерфейсу и журналу:

| Метрика | Источник | Норма / плохо |
|---|---|---|
| Входящий битрейт | `webrtc/stats.py`, `RTCTransportStats.bytesReceived`, раз в секунду | — |
| Потери, % | там же, дельты `packetsLost` / `packetsReceived` | < 1 % / > 3 % |
| Задержка p95 | `ping-channel`, опрос 5 Гц, перцентиль за 10 с | < 150 мс / > 400 мс |
| Замирания | интервалы между показанными кадрами в `VideoManager` | < 1 % времени / > 5 % |
| Исходящий битрейт борта и доля от заказанного | сообщение `stats` config-канала | > 90 % / < 70 % |
| Запросы ключевого кадра (PLI) | там же | 0–2 в минуту |

Замиранием считается интервал между кадрами больше `max(3 × средний, средний +
150 мс)` — определение из webrtc-stats. Рост задержки отслеживается отдельно от
потерь: на мобильных сетях перегрузка проявляется ростом задержки при нулевых
потерях, и регулятор, следящий только за потерями, её не увидит.

Ограничения `aiortc`, которые пришлось обойти: `RTCInboundRtpStreamStats`
содержит только `packetsReceived`, `packetsLost` и `jitter` — байт там нет,
поэтому битрейт берётся с транспорта целиком; `packetsLost` уменьшается при
дубликатах, поэтому дельта ограничивается снизу нулём; свойство
`fraction_lost` читать нельзя — оно сбрасывает счётчики, по которым библиотека
формирует RTCP-отчёты.

Светофор в интерфейсе — производная от потерь, роста задержки, доли замираний
и недобора битрейта энкодером. Полная таблица открывается клавишей `S`.
Отдельный индикатор показывает возраст кадра, если картинка не обновлялась
дольше 300 мс: пилот не должен принимать замершее изображение за реальность.

#### 4.4.1. Рекомендация режима камеры

Модуль `ui/managers/advisor.py` (`Advisor`) пристраивается к той же таблице
качества и раз в 5 секунд (в `App._tick_quality`, каждый пятый тик таймера)
считает, какой режим камеры (разрешение × fps) сейчас подходит каналу —
и показывает подсказку под таблицей `S`. Ничего не переключает сам —
решение остаётся за пилотом (`Desktop → Board`, сообщение `params`,
отправляется только по кнопке «Сохранить»).

Нужный битрейт считается формулой Kush Gauge:
`required = width × height × fps × bpp × motion / 1000` (кбит/с), где `bpp`
(бит на пиксель на кадр) и `motion` (множитель динамики картинки) — константы
из конфигурации (`VIDEO_BPP`, `VIDEO_MOTION_FACTOR`, см. §6.3).

Доступная ёмкость канала (`ChannelEstimator`) оценивается так:

- база — фактический входящий goodput (`LinkSnapshot.bitrate_in_kbps`);
- **канал чистый** (потери < 0.5 % и рост задержки < ×1.2) — `goodput × 1.15`,
  а после 30 с непрерывной чистоты `goodput × 1.5` (осторожная проба);
- **умеренные помехи** (потери до 5 %, рост задержки до ×1.5) — `goodput`
  без поправок: раз столько байт реально прошло, столько канал и даёт;
- **перегрузка** (потери > 5 % или рост задержки ≥ ×1.5) — `goodput × 0.85`,
  дополнительно ограниченное уравнением пропускной способности TFRC
  (RFC 5348) от RTT p95 и доли потерь, но не ниже половины goodput;
- итог сглаживается экспоненциальным средним (EWMA, α = 0.3), чтобы разовый
  всплеск не дёргал рекомендацию.

Про TFRC важно понимать, что он отвечает на вопрос «какую скорость поток
занимал бы честно рядом с TCP», а не «сколько канал вмещает»: при 1 % потерь
и RTT 50 мс формула даёт около 1.6 Мбит/с, хотя видео в этот момент может
спокойно идти на 4 Мбит/с. Поэтому TFRC применяется только при реальной
перегрузке и снизу ограничен половиной фактического goodput.

Осторожность с ростом принципиальна по другой причине: goodput ограничен уже
заказанным нами битрейтом, поэтому «наверх» рекомендация двигается маленькими
пробными шагами и только на давно чистом канале — иначе легко принять
«мы сами себя ограничили» за «канал больше не может».

Из списка режимов камеры выбирается самый крупный (по width × height, при
равенстве — по fps), для которого `required × 1.25 ≤ capacity` (запас 25 %)
и `fps` не выше зафиксированного `VideoManager.rendered_fps()` больше чем на 5.
**Текущий режим при этом не понижается, пока он влезает без запаса**
(`required ≤ capacity`): иначе работающий режим постоянно предлагалось бы
понизить на ступень только из-за недобора 25 % запаса. Если ни один режим не
проходит — подсказывается минимальный доступный, а во второй строке
помечается, что канал не тянет и его.

Смена рекомендации требует двух одинаковых результатов подряд (гистерезис
в 2 тика × 5 с = 10 с) — иначе подсказка будет мигать между соседними
режимами на границе. Первые 10 секунд сессии подсказка не показывается —
метрикам ещё не на чем накопиться.

Метрики пишутся построчно в `~/.config/mavixdesktop/logs/stats_<дата>.jsonl`
(одна запись в секунду, около мегабайта за час) — по этому файлу разбирается
уже состоявшийся полёт.

## 6. Установка

### 6.1. Установка через `.deb`-пакет (рекомендуется)

```bash
sudo apt update
sudo apt install ./mavixdesktop.deb
```

Установщик:

- создаёт виртуальное окружение `/opt/mavixdesktop/.venv`;
- устанавливает Python-зависимости из PyPI (PySide6, aiortc,
  numpy и др.);
- регистрирует ярлык приложения в меню рабочего стола.

Запуск из меню: «Network → Mavix Desktop» или командой:

```bash
/opt/mavixdesktop/.venv/bin/python -m mavixdesktop
```

### 6.2. Установка для разработки

```bash
git clone https://github.com/AurunChill/MavixDesktop.git
cd MavixDesktop
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
cp .env-example .env
# Отредактировать .env
.venv/bin/python -m mavixdesktop
```

### 6.3. Параметры конфигурации

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `SIGNAL_URL` | Базовый URL сервера | `http://localhost:8000` |
| `SIGNAL_WS_URL` | Полный URL WebSocket (если задан, переопределяет) | пусто |
| `STUN_SERVER`, `TURN_SERVER`, `TURN_USERNAME`, `TURN_PASSWORD` | WebRTC ICE-серверы | пусто (берутся с сервера) |
| `QGC_HOST`, `QGC_PORT` | Адрес и порт UDP-сокета QGroundControl | `127.0.0.1`, `14550` |
| `QGC_BIND_PORT` | Локальный порт для приёма от QGC | `0` (выбирается ОС) |
| `VIDEO_BPP` | Бит на пиксель на кадр (H.264) для расчёта рекомендации режима, см. §4.4.1 | `0.07` |
| `VIDEO_MOTION_FACTOR` | Множитель динамики картинки: 1 — статика, 2 — обычный полёт, 4 — быстрое панорамирование | `2.0` |
| `KEYRING_SERVICE` | Имя сервиса в системном хранилище секретов | `mavixdesktop` |
| `DEBUG` | Старт на debug-странице (ручная проверка функций без борта/сервера) + лог на уровне DEBUG. Только при запуске из исходников | `0` |

#### Порядок приоритета источников конфигурации

При запуске значения берутся из перечисленных источников; более высокий
в списке источник переопределяет более низкий:

1. Переменные окружения операционной системы.
2. Файл `~/.config/mavixdesktop/config.json` — то, что пользователь задал на
   экране настроек (`core/user_config.py`). Значения из него подставляются в
   окружение только там, где переменная ещё не задана, поэтому системный env
   остаётся главнее.
3. Файл `.env` в корне репозитория (dev-fallback; в prod-сборке
   PyInstaller отсутствует).
4. Значения по умолчанию, заданные в коде (`core/config.py`).

Для production-сборки достаточно одного из двух способов задания
адреса сервера сигнализации:

- пользователь задаёт адрес на экране настроек (сохраняется в
  `~/.config/mavixdesktop/config.json`) либо выставляет переменную окружения
  `SIGNAL_URL` перед запуском бинарника;
- значение по умолчанию `signal_url` правится прямо в
  `core/config.py` перед сборкой single-file binary через
  `pyinstaller mavixdesktop.spec`.

#### Debug-режим

При `DEBUG=1` в `.env` приложение стартует на debug-странице
(`ui/screens/debug_page.py`), минуя логин, и пишет лог на уровне `DEBUG`.
Страница содержит кнопки ручной проверки отдельных функций без борта и
сервера — сейчас это «Запуск QGroundControl» (тот же путь, что и в
полётном режиме: фоновый поиск со спиннером, запуск найденного QGC либо
диалог выбора пути). Режим предназначен для запуска из исходников
(`python -m mavixdesktop`); в PyInstaller-бандле `.env` не читается.

сервера.

## 8. Сообщения системному программисту

| Сообщение | Причина | Действия |
|---|---|---|
| `signal server unreachable` | Невозможно достичь сервера | Проверить URL и сетевое соединение |
| `login failed: invalid credentials` | Неверные данные | Проверить ввод; при необходимости — сбросить пароль через сервер |
| `[connection] refresh failed` | Просроченный refresh-токен | Программа автоматически переходит на экран входа |
| `[coord] auto-reconnecting to drone ...` | Дрон, который только что отключился, снова доступен | Штатная ситуация |
| `[qgc] QGroundControl не найден` | Не найден исполняемый файл QGC | Указать путь вручную в диалоге, установить QGroundControl или продолжить работу без него |
| `[mavlink-relay] sendto error` | UDP-сокет QGC недоступен | Запустить QGroundControl |

## 9. Журналирование

Журнал ведётся в:

- стандартный поток вывода (видим при запуске из терминала);
- файл `~/.config/mavixdesktop/logs/mavixdesktop_<дата>.log`.

Уровни сообщений: `INFO`, `WARNING`, `ERROR`. По умолчанию — `INFO`.

Файл журнала ротируется: 10 МБ на файл, 5 архивных копий
(`mavixdesktop_<дата>.log.1` … `.5`), не более 60 МБ суммарно.

В журнал дополнительно попадают:

- необработанные исключения, в том числе возникшие в рабочих потоках
  (уровень `CRITICAL`, со стеком вызовов). Без этого в собранном одним
  файлом бинарнике сбой не виден нигде — стандартный поток ошибок
  показывать некому;
- сообщения самого Qt (префикс `[qt]`) — они по умолчанию идут в
  стандартный поток ошибок мимо журнала;
- предупреждения и ошибки библиотек `aiortc`, `aioice`, `av`,
  `websockets`, `asyncio`.

Переменная окружения `ICE_DEBUG=1` дополнительно переводит `aioice` и
`aiortc` на уровень `DEBUG` — для разбора неудачных ICE-соединений.

## 10. Безопасность учётных данных

- Refresh-токен хранится в системном хранилище секретов (gnome-keyring
  / KWallet / Keychain). Доступ к токену имеет только пользователь,
  под которым выполняется программа.
- При отсутствии хранилища секретов используется JSON-файл
  `~/.config/mavixdesktop/tokens.json` с правами `0600`.
- Access-токен живёт в оперативной памяти процесса и не сохраняется
  на диск.
- При нажатии «Выйти» (logout) токен из хранилища удаляется.
